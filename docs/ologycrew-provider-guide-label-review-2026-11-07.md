## Discrepancies and unresolved publication choices

1. **Existing Help content needs owner reconciliation, not automatic replacement.** `HelpCenter.tsx:378–380` already has a customer-oriented **Pay at Location** article, but **How Payments Work** (`373–375`) and **How are payments processed?** (`505–507`) say all payments use Stripe. **Understanding the Platform** (`111–113`), **Privacy & Security** (`441–443`), and the booking FAQ (`469–471`) also use broad Stripe wording. **Platform Fees** (`383–385`) and **Refunds & Cancellations** (`401–404`) should not be carried over as blanket offline claims. Choose **For Providers** versus **Payments & Billing** placement, and whether to retain the existing customer article alongside the provider article, only upon explicit publication approval. No Help content was changed.
2. **Adjacent Stripe checkout is not visibly offline-ledger gated in this source.** `server/stripeRouter.ts:21–49,51–265` does not read `getOfflinePaymentForBooking` or reject a Pay at Location ledger. Its completed-payment guard (`66–73`) is for captured online payments; `server/paymentAuthorization.ts` checks actor/provider/payment entitlement, not offline booking type. The corrected confirmation UI gates checkout correctly, and the supplied isolated walkthrough reports zero Stripe requests. That evidence does not establish direct-route exclusion. Keep the article's no-charge statement scoped to the offline UI flow; owner/release reviewers should resolve this source qualification before asserting a system-wide guarantee. No route was called and no payment feature was rewritten.
3. **Legacy booking-list prompt differs from the corrected confirmation.** `MyBookings.tsx:1037–1046` renders **Pay Now** for confirmed customer bookings without `booking.paidAt`; its `isOffline` is network connectivity, not Pay at Location ledger state (`137–141`). Offline settlement leaves booking lifecycle/`booking.paidAt` separate. Static source therefore permits a generic list prompt even when the offline record is Paid/Waived; following it reaches the ledger-gated confirmation. The article instructs providers/customers not to charge twice and to stop on inconsistency. This was not runtime-tested here and does not reopen the accepted visual walkthrough as failed.
4. **Search and navigation vary.** Searching “Pay at Location” can hide **Pricing & payments** because only tips/estimates/payment-group keywords are indexed (`ProviderDashboard.tsx:1779–1801`). The clear-search instruction handles this without source changes. The older Help booking article still describes “Bookings I Made” / “Bookings I Received” tabs (`HelpCenter.tsx:124–126`); current `MyBookings.tsx` uses role view instead. Draft uses current labels.
5. **Receipt capitalization and history semantics vary.** Detail/method selector uses **Bank transfer** / **Mobile money** from `shared/offlinePaymentPresentation.ts`; confirmation renders raw method values with underscores replaced (`BookingConfirmation.tsx:311`), yielding “bank transfer” / “mobile money”. Confirmation history labels are **Recorded by user**, **Payment recorded**, **Waived by user**, **Payment waived**, versus detail's user-ID/time labels. Provider instructions are current settings, not historical snapshots. Do not imply an immutable instruction archive, receipt download, private note, or named-provider signature.
6. **Remaining gates are not completed by these drafts.** Owner article approval, separately authorized isolated full-suite regression, target-release/live label parity, production deployment decision, and pilot/account selection remain separate. No current production disabled state or global flag was remeasured. Preserve the existing authorization boundary; neither Markdown file grants access or is a release sign-off.
